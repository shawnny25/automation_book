개념 정리

프로그램이란

컴퓨터는 시킨 순서대로만 움직이는 아주 빠른 신입 직원입니다. 프로그램은 입력 → 처리 → 출력으로 이루어진 업무 매뉴얼입니다. 예를 들어 예산 엑셀(입력)을 읽고, 집행률을 계산하고(처리), 요약 파일을 만드는(출력) 일이 하나의 프로그램입니다. Python은 문법이 영어 문장에 가깝고 엑셀·문서·API를 다루는 도구가 풍부해서 업무 자동화에 가장 많이 쓰입니다.

변수와 자료형

변수는 이름표가 붙은 상자입니다. 값을 상자에 넣어 두고 이름으로 꺼내 씁니다.

budget = 12000000    # 정수(int)
name = "A사업"        # 문자열(str): 따옴표로 감싼 글자
rate = 79.2          # 실수(float): 소수점이 있는 숫자
is_over = False      # 불리언(bool): True 또는 False
  • =는 "같다"가 아니라 "오른쪽 값을 왼쪽 상자에 넣는다"는 뜻입니다. 같은지 비교할 때는 ==를 씁니다.
  • 자료형에 따라 같은 +도 다르게 동작합니다. 100 + 200은 300이지만 "100" + "200"은 글자를 이어 붙여 "100200"이 됩니다.
  • 엑셀에서 읽어 온 숫자가 문자로 들어오는 경우가 많습니다. type(값)으로 자료형을 확인하세요.
  • 흔한 실수: 숫자와 문자열을 더해서 TypeError가 납니다. 해결은 int("100")처럼 형을 바꾸는 것입니다.

리스트와 딕셔너리

리스트는 번호표가 붙은 서랍장입니다(순서가 있음). 딕셔너리는 이름표가 붙은 서랍장입니다(키로 값을 찾음).

items = ["인건비", "사업비", "운영비"]
items[0]                      # "인건비" (번호는 0부터 시작)

budget = {"인건비": 12000000, "사업비": 8000000}
budget["사업비"]               # 8000000
budget["홍보비"] = 2000000     # 새 항목 추가
budget.get("기타", 0)          # 없는 키는 0으로 (에러 방지)

엑셀로 비유하면 리스트는 한 열(또는 한 행), 딕셔너리는 "항목명 → 금액" 두 칸짜리 표입니다. 흔한 실수는 번호를 1부터 세는 것, 그리고 없는 키를 찾아 KeyError가 나는 것입니다.

조건문

"만약 ~라면 이렇게, 아니면 저렇게"를 코드로 쓴 것입니다.

if spent > budget:
    print("예산 초과")
elif spent / budget < 0.8:
    print("집행 저조")
else:
    print("정상")
  • 비교 연산자: >, <, >=, <=, ==(같다), !=(다르다). 여러 조건은 and, or, not으로 묶습니다.
  • 위에서부터 검사해서 처음 참인 것 하나만 실행합니다.
  • Python에서는 들여쓰기(4칸)가 문법입니다. 들여쓴 줄만 그 조건 안에 속합니다.
  • 흔한 실수: == 대신 = 사용, 줄 끝 콜론(:) 빠뜨림, 들여쓰기 어긋남.

반복문

같은 일을 목록의 항목마다 되풀이합니다. 엑셀에서 수식을 아래로 쭉 끌어 채우는 것과 같습니다.

total = 0                      # 합계 상자를 0으로 시작
for amount in [3000000, 2400000, 250000]:
    total += amount            # total = total + amount
print(total)                   # 5650000

for item, money in budget.items():   # 딕셔너리는 키와 값을 함께 꺼냄
    print(item, money)

핵심 패턴은 누적입니다. 합계 변수를 0으로 만들어 두고 반복하며 더해 갑니다. 흔한 실수는 합계를 0으로 초기화하지 않는 것, 그리고 print(total)을 들여써서 매번 출력되게 만드는 것입니다.

함수

함수는 입력을 받아 결과를 돌려주는 상자입니다. 같은 계산을 여기저기 복사하는 대신 이름을 붙여 재사용하고, 고칠 때도 한 곳만 고치면 됩니다.

def rate(spent, budget):
    return round(spent / budget * 100, 1)

rate(9500000, 12000000)   # 79.2
  • def로 만들고(정의), 이름으로 부릅니다(호출). 정의만 하고 호출하지 않으면 아무 일도 일어나지 않습니다.
  • print는 화면에 보여줄 뿐이고, return은 값을 돌려줘서 다른 계산에 쓸 수 있게 합니다.
  • 흔한 실수: return을 빼먹으면 결과가 None이 됩니다. 예산이 0이면 ZeroDivisionError가 나므로 조건문으로 미리 막아야 합니다.

라이브러리와 엑셀 구조

라이브러리는 남이 만들어 둔 도구 상자입니다. pip install 이름으로 설치하고 import로 꺼내 씁니다. 엑셀은 워크북(파일) → 워크시트 → 셀(행·열) 구조이고, openpyxl이 이 구조를 그대로 다룹니다.

from openpyxl import load_workbook

ws = load_workbook("sample_budget.xlsx")["예산"]      # 파일 열고 시트 선택
for row in ws.iter_rows(min_row=2, values_only=True):   # 2행부터(머리글 제외)
    print(row)    # ('A사업', '인건비', 12000000, 9500000)

한 행은 값 묶음(튜플)으로 나오므로 사업명, 항목, 예산액, 집행액 = row처럼 한 번에 풀어 받을 수 있습니다. 흔한 실수: 엑셀 파일이 열려 있어 저장이 막히는 것, 경로 오타로 FileNotFoundError, 시트 이름 오타로 KeyError.

에러 메시지 읽는 법

에러가 나도 당황하지 않아도 됩니다. 맨 아래 한 줄에 종류와 이유가 있습니다(예: KeyError: '홍보비'는 "홍보비라는 키가 없다"). 그 위 줄들은 "어느 파일 몇 번째 줄에서"를 알려 줍니다. 전체를 복사해 Claude에게 붙여 넣으면 가장 빠르게 해결됩니다.

"""1주차: 엑셀을 읽어 항목별 예산·집행액 합계를 구한다. (openpyxl만 사용)

    """집행률(%) = 집행액 / 예산액 * 100"""
    return round(spent / budget * 100, 1)


ws = load_workbook(SRC)["예산"]

    totals[item][1] += spent

개념 정리

왜 pandas인가

1주차의 반복문으로도 합계는 구할 수 있지만, 수천 행의 표에서 필터링·그룹 합계·병합까지 하려면 코드가 길어집니다. pandas는 엑셀 시트를 통째로 다루는 도구입니다. "열 전체에 한 번에", "조건에 맞는 행만", "항목별로 묶어서" 같은 작업을 한두 줄로 합니다.

DataFrame: 코드 속의 엑셀 시트

DataFrame은 행과 열이 있는 표입니다. 엑셀 시트 하나가 DataFrame 하나입니다.

  • 열(column): 항목 하나의 값 모음. 예: df["예산액"]
  • 행(row): 한 건의 기록. 예: A사업 인건비 한 줄
  • 인덱스(index): 행 번호표. 기본은 0, 1, 2…
import pandas as pd

df = pd.read_excel("sample_budget.xlsx", sheet_name="예산")
df.head()    # 앞 5행 미리보기
df.shape     # (8, 4) = 8행 4열
df.info()    # 열 이름, 자료형, 빈 칸 수

불러오면 가장 먼저 head(), shape, info() 세 가지로 내가 생각한 표와 같은지 확인하는 습관을 들이세요. 자동화에서 가장 많은 사고는 "데이터가 생각과 달랐던 것"에서 납니다.

선택과 필터링

df["집행액"]                          # 열 하나 선택 (Series)
df[["항목", "집행액"]]                # 열 여러 개 선택 (대괄호 두 겹)
df[df["집행액"] > 8000000]            # 조건에 맞는 행만
df[(df["사업명"] == "A사업") & (df["집행액"] > 5000000)]   # 조건 여러 개
df.sort_values("집행액", ascending=False)   # 큰 순서로 정렬

조건식 df["집행액"] > 8000000은 행마다 True/False를 만들고, 바깥 df[...]가 True인 행만 남깁니다. 조건을 둘 이상 묶을 때는 and가 아니라 &, or가 아니라 |를 쓰고, 각 조건을 괄호로 감싸야 합니다. 이 괄호를 빼먹는 것이 가장 흔한 에러입니다.

열 연산: 반복문 없이 한 번에

df["집행률"] = (df["집행액"] / df["예산액"] * 100).round(1)

엑셀에서 첫 행에 수식을 넣고 아래로 채우는 일을, pandas는 열 전체에 한 번에 적용합니다(벡터화). 반복문보다 짧고 훨씬 빠릅니다. 없는 열 이름에 값을 넣으면 새 열이 만들어집니다.

groupby: 쪼개기 → 계산 → 합치기

엑셀의 피벗 테이블과 같은 개념입니다.

df.groupby("사업명")[["예산액", "집행액"]].sum()
  1. 쪼개기: 사업명이 같은 행끼리 묶는다 (A사업 묶음, B사업 묶음)
  2. 계산: 각 묶음에서 합계를 구한다 (sum, mean, count, max 등)
  3. 합치기: 결과를 한 표로 모은다

주의할 점: 집행률 같은 비율의 합계는 구하면 안 됩니다. 사업별 집행률은 항목별 집행률을 더하는 게 아니라, 합계 예산과 합계 집행액을 구한 뒤 다시 나눠야 정확합니다.

결측치와 자료형

빈 칸은 pandas에서 NaN(값 없음)으로 읽힙니다. 숫자 열에 NaN이 섞이면 합계는 NaN을 건너뛰고, 나눗셈 결과는 NaN이 됩니다.

df["증빙유형"].isna()                  # 빈 칸 여부 (True/False)
df["집행액"].fillna(0)                 # 빈 칸을 0으로 채우기
df.dropna(subset=["증빙유형"])         # 빈 칸 있는 행 지우기
df["금액"] = df["금액"].astype(str).str.replace(",", "").astype(int)   # "1,200,000" → 1200000

엑셀에서 숫자를 "1,200,000"처럼 글자로 저장해 두면 계산이 되지 않습니다. 의도적으로 비운 칸(증빙 누락)을 0으로 채워 버리면 오류를 숨기게 되므로, 채우기 전에 "이 빈 칸은 오류 신호인가, 정상인가"를 먼저 판단하세요.

흔한 에러

  • KeyError: '집행율': 열 이름 오타. df.columns로 실제 이름을 확인합니다. 열 이름 앞뒤 공백도 원인이 됩니다.
  • ValueError: ... truth value of a Series is ambiguous: 조건에 and/or를 썼을 때 납니다. &/|와 괄호로 바꿉니다.
  • 저장한 엑셀에 왼쪽에 0, 1, 2 번호 열이 생김: to_excel(..., index=False)로 인덱스 저장을 끕니다.

그 빈 칸이 정상인지, 증빙 누락 같은 오류 신호인지입니다. 오류 신호를 0으로 덮으면 문제가 숨습니다.

"""2주차: pandas로 집행률을 계산하고 80% 미만·100% 초과 칸에 색을 입힌다.

실행: python week2/week2_execution_rate.py
필요: pip install pandas openpyxl
"""
from pathlib import Path
import pandas as pd
from openpyxl import load_workbook
from openpyxl.styles import PatternFill

BASE = Path(__file__).resolve().parent.parent
OUT = BASE / "week2_result.xlsx"

df = pd.read_excel(BASE / "sample_budget.xlsx", sheet_name="예산")
print(df.head(), df.shape, sep="\n")  # 월요일 실습: 표의 모양 확인

print(df[df["집행률"] > 100])

# 집계: 사업별·항목별 합계 (쪼개기 -> 계산 -> 합치기)
by_project = df.groupby("사업명")[["예산액", "집행액"]].sum()

print("\n[사업별]")
print(by_project)

# 엑셀 저장 후 조건부 색칠
with pd.ExcelWriter(OUT) as w:
    df.to_excel(w, sheet_name="상세", index=False)
    by_project.to_excel(w, sheet_name="사업별")

wb = load_workbook(OUT)
ws = wb["상세"]
red = PatternFill("solid", fgColor="FFC7CE")     # 100% 초과
yellow = PatternFill("solid", fgColor="FFEB9C")  # 80% 미만

for r in range(2, ws.max_row + 1):

    if cell.value > 100:
        cell.fill = red
    elif cell.value < 80:
        cell.fill = yellow
wb.save(OUT)
print(f"\n저장: {OUT}")

개념 정리

규칙 기반 처리: 규칙은 코드 밖에 둔다

정산 점검은 "인건비는 건당 350만 원 이하", "운영비는 영수증 필수" 같은 규칙의 집합입니다. 이 규칙을 if 문으로 코드 안에 박아 넣으면 기준이 바뀔 때마다 코드를 고쳐야 하고, 어디를 고쳤는지 추적하기도 어렵습니다. 그래서 규칙은 표(데이터) 로 따로 두고, 코드는 "표를 읽어 적용하는 일"만 합니다.

RULES = pd.DataFrame(
    [("인건비", 3500000, "급여명세서"), ("운영비", 300000, "영수증,세금계산서")],
    columns=["항목", "건당한도", "인정증빙"],
)

이렇게 하면 기준이 바뀔 때 표만 고치면 되고, 담당자가 코드를 몰라도 엑셀 규칙표를 직접 관리할 수도 있습니다. 규칙이 코드와 분리되어 있다는 점이 "자동화를 오래 쓸 수 있는가"를 가르는 핵심입니다.

merge: 두 표를 열쇠로 붙이기

엑셀의 VLOOKUP(XLOOKUP)과 같은 역할입니다. 공통 열(키)을 기준으로 두 표를 옆으로 붙입니다.

exp = exp.merge(RULES, on="항목", how="left")
  • on="항목": 이 열의 값이 같은 행끼리 연결
  • how="left": 왼쪽 표(지출내역)의 행은 하나도 잃지 않고 유지. 규칙이 없는 항목은 규칙 칸이 빈 값(NaN)
  • 붙인 뒤에는 exp["건당한도"].isna().sum()으로 규칙이 없는 지출이 몇 건인지 꼭 확인하세요. 점검 대상이 조용히 빠지는 것을 막아 줍니다.

규칙 적용: 한 열에 한 질문

exp["한도초과"] = exp["금액"] > exp["건당한도"]
exp["증빙누락"] = exp["증빙유형"].isna()
issues = exp[exp[["한도초과", "증빙누락"]].any(axis=1)]   # 하나라도 True인 행

점검 항목마다 True/False 열을 하나씩 만들어 두면 어떤 건이 왜 걸렸는지 결과표에 그대로 남습니다. any(axis=1)은 "행 방향으로 하나라도 True인가", all(axis=1)은 "모두 True인가"입니다. 자동 점검은 의심 후보를 추려 주는 도구이지 최종 판정이 아닙니다. 걸린 건을 사람이 확인하는 단계를 업무 흐름에 반드시 넣으세요.

데이터베이스와 SQL

엑셀 파일은 편하지만 수만 건, 여러 사람이 동시에 쓰는 데이터, 여러 표의 연결에는 한계가 있습니다. 데이터베이스(DB) 는 표를 안전하고 빠르게 보관·조회하는 저장소이고, SQL은 그 저장소에 "이런 데이터를 꺼내 줘"라고 묻는 언어입니다.

  • 테이블: 엑셀 시트 하나 (예: expense)
  • 행(레코드): 한 건의 기록
  • 열(컬럼): 항목 하나. 각 열에는 자료형이 정해져 있음
  • 기본키(Primary Key): 행마다 겹치지 않는 고유 번호. 한 건을 정확히 가리키는 주민번호 같은 역할
  • SQLite: 파일 하나가 곧 DB인 가장 가벼운 DB. 설치 없이 Python에 들어 있어 연습에 알맞음

SQL 기본 문장 읽는 법

SQL은 "무엇을 → 어디서 → 어떤 조건으로" 순서의 영어 문장처럼 읽습니다.

SELECT 지출일, 항목, 금액     -- 어떤 열을 보여줄지
FROM expense                 -- 어느 테이블에서
WHERE 금액 >= 500000         -- 어떤 행만 (엑셀의 필터)
ORDER BY 금액 DESC;          -- 정렬 (DESC는 큰 순서)
  • SELECT *는 모든 열입니다.
  • 문자 조건은 작은따옴표를 씁니다: WHERE 사업명 = 'A사업'
  • 조건을 묶을 때는 AND, OR를 씁니다.

GROUP BY와 집계 함수

2주차의 groupby와 같은 개념입니다. 엑셀 피벗 테이블이라고 생각하세요.

SELECT 사업명, SUM(금액) AS 합계, COUNT(*) AS 건수
FROM expense
GROUP BY 사업명;
  • 집계 함수: SUM(합), COUNT(건수), AVG(평균), MAX/MIN
  • AS 합계: 결과 열에 이름 붙이기
  • 규칙: SELECT에 쓴 열 중 집계 함수가 아닌 열은 반드시 GROUP BY에도 있어야 합니다.
  • WHERE는 묶기 전에 행을 거르고, HAVING은 묶은 뒤에 결과를 거릅니다 (예: 합계가 100만 원 넘는 사업만).

JOIN: 표 연결하기

merge와 같은 개념을 SQL로 쓴 것입니다. 데이터를 표 하나에 몰아넣지 않고 주제별로 나눠 저장(예산 표, 지출 표)한 뒤, 필요할 때 키로 연결합니다. 같은 정보를 여러 곳에 중복 저장하지 않아 수정할 때 한 곳만 고치면 됩니다.

SELECT b.사업명, b.항목, b.예산액, SUM(e.금액) AS 지출합계
FROM budget b
JOIN expense e ON b.사업명 = e.사업명 AND b.항목 = e.항목
GROUP BY b.사업명, b.항목;
  • budget b: budget 표에 b라는 별명을 붙여 쓰기 쉽게 함
  • ON ...: 어떤 열이 같으면 같은 행으로 볼지(연결 조건)
  • JOIN(INNER JOIN)은 양쪽에 모두 있는 행만 남깁니다. 지출이 한 번도 없는 예산 항목까지 보고 싶다면 LEFT JOIN을 씁니다. 샘플에서 직접 바꿔 비교해 보세요.

흔한 실수

  • 연결 조건을 빼먹으면 두 표의 모든 조합이 나와 행이 폭증합니다(8행 × 12행 = 96행).
  • 날짜를 글자로 저장한 경우 월별 집계는 substr(지출일, 1, 7)로 앞 7글자(2026-03)만 잘라 씁니다.
  • 엑셀의 금액이 글자로 들어가면 SUM이 엉뚱하게 나옵니다. DB에 넣기 전에 자료형을 맞추세요.

복습 질문

1. 정산 규칙을 코드 안이 아니라 표로 따로 두는 이유는 무엇인가요?

기준이 바뀔 때 코드를 고치지 않고 표만 고치면 되고, 무엇이 바뀌었는지 추적하기 쉽기 때문입니다.

2. merge의 how="left"는 어떤 뜻인가요?

왼쪽 표의 행을 하나도 잃지 않고 유지하고, 짝이 없는 행은 붙인 열이 빈 값이 됩니다.

3. SQL에서 WHERE와 HAVING은 무엇이 다른가요?

WHERE는 묶기 전에 행을 거르고, HAVING은 묶어서 계산한 뒤 결과를 거릅니다.

4. JOIN에서 연결 조건(ON)을 빼먹으면 어떻게 될까요?

두 표의 모든 조합이 만들어져 행이 폭증합니다. 8행과 12행이면 96행이 됩니다.

"""3주차: 정산 규칙을 '표'로 분리해 지출내역을 자동 점검한다.

규칙(한도·필수 증빙)은 코드가 아니라 RULES 표에 있다. 규칙이 바뀌면 표만 고치면 된다.
아래 규칙은 연습용 가짜 기준입니다. 실제 업무에서는 기관의 정산 기준으로 바꾸세요.

실행: python week3/week3_rules_check.py
"""
from pathlib import Path
import pandas as pd

BASE = Path(__file__).resolve().parent.parent

# 항목별 1건당 한도(원)와 인정되는 증빙
RULES = pd.DataFrame(
    [
        ("인건비", 3_500_000, "급여명세서"),
        ("사업비", 2_000_000, "세금계산서,영수증"),
        ("운영비", 300_000, "영수증,세금계산서"),
        ("홍보비", 500_000, "세금계산서"),
    ],
    columns=["항목", "건당한도", "인정증빙"],
)

exp = pd.read_excel(BASE / "sample_budget.xlsx", sheet_name="지출내역")
exp = exp.merge(RULES, on="항목", how="left")  # 지출 내역에 규칙을 붙인다

exp["한도초과"] = exp["금액"] > exp["건당한도"]
exp["증빙누락"] = exp["증빙유형"].isna()
# 증빙은 있으나 인정 증빙이 아닌 경우
exp["증빙부적합"] = ~exp["증빙누락"] & ~exp.apply(
    lambda r: r["증빙유형"] in str(r["인정증빙"]).split(","), axis=1
)

issues = exp[exp[["한도초과", "증빙누락", "증빙부적합"]].any(axis=1)]
print(f"점검 {len(exp)}건 중 확인 필요 {len(issues)}건")
print(issues[["지출일", "사업명", "항목", "금액", "설명", "한도초과", "증빙누락", "증빙부적합"]])

exp.to_excel(BASE / "week3_check_result.xlsx", index=False)
issues.to_excel(BASE / "week3_issues.xlsx", index=False)

assert exp["증빙누락"].sum() == 2  # 샘플: 다과비, 현수막

지출 내역을 SQLite에 넣고 SELECT, GROUP BY, JOIN을 연습합니다.

"""3주차: 지출내역을 SQLite(DB)에 넣고 SQL로 조회해 본다.

SQL 문장(SELECT ...)을 눈으로 읽고, 한 줄씩 바꿔 실행해 보는 것이 이 파일의 목적입니다.
실행: python week3/week3_sql_practice.py
"""
import sqlite3
from pathlib import Path
import pandas as pd

BASE = Path(__file__).resolve().parent.parent
DB = BASE / "practice.db"

con = sqlite3.connect(DB)
# 엑셀의 두 시트를 DB 테이블 두 개로 옮긴다 (이미 있으면 덮어씀)
pd.read_excel(BASE / "sample_budget.xlsx", sheet_name="예산").to_sql("budget", con, if_exists="replace", index=False)
pd.read_excel(BASE / "sample_budget.xlsx", sheet_name="지출내역").to_sql("expense", con, if_exists="replace", index=False)


def show(title, sql):
    print(f"\n## {title}\n{sql.strip()}")
    print(pd.read_sql(sql, con).to_string(index=False))


# 금요일: SELECT / WHERE / ORDER BY
show("50만원 이상 지출, 큰 금액순", """
SELECT 지출일, 사업명, 항목, 금액 FROM expense
WHERE 금액 >= 500000

""")
show("월별 지출 합계", """
SELECT substr(지출일, 1, 7) AS 월, SUM(금액) AS 합계

""")

SELECT b.사업명, b.항목, b.예산액, SUM(e.금액) AS 지출합계
FROM budget b JOIN expense e ON b.사업명 = e.사업명 AND b.항목 = e.항목
GROUP BY b.사업명, b.항목
""")

con.close()

# 자기 점검: 지출내역 12건, 합계 15,500,000원

개념 정리

설계 원칙: 코드는 계산, AI는 언어

4주차에서 가장 중요한 한 줄입니다. 정확해야 하는 일(계산, 규칙 판정, 합계)은 코드가 하고, 말을 다루는 일(분류, 요약, 문장 작성)은 AI가 합니다. 코드는 같은 입력에 항상 같은 결과를 내지만, AI는 그럴듯한 답을 만들 뿐 계산을 보장하지 않습니다. 그래서 3주차까지 만든 점검 결과(숫자, 위반 여부)는 코드가 확정하고, AI는 그 결과를 사람이 읽기 좋은 문장으로 바꾸는 역할만 맡깁니다.

LLM이란

LLM(대규모 언어 모델)은 방대한 글을 학습해서 "지금까지의 글 다음에 올 가장 알맞은 조각"을 하나씩 예측하는 모델입니다. 글을 정리하고 분류하고 쓰는 일에 뛰어난 이유이자, 사실이 아닌 내용을 자신 있게 쓰는 환각(hallucination) 이 생기는 이유입니다. 모델은 "사실을 조회"하는 것이 아니라 "그럴듯한 문장을 생성"합니다.

  • 토큰: 모델이 글을 읽는 단위(단어나 글자 조각). 한 번에 처리할 수 있는 길이 한도와 API 요금이 모두 토큰 기준입니다. 한국어는 같은 내용이라도 영어보다 토큰이 더 많이 쓰이는 경향이 있습니다.
  • 컨텍스트 윈도우: 모델이 한 번에 읽을 수 있는 양. 이 안에 들어간 내용만 모델이 알고 답합니다.
  • 같은 질문에도 답이 조금씩 달라질 수 있습니다. 자동화에서는 "JSON으로만 출력"처럼 출력 형식을 엄격히 정해서 이 흔들림을 줄입니다.

API란

API는 프로그램이 다른 프로그램에게 일을 시키는 창구입니다. 식당에 비유하면 손님(내 코드)이 주문서(요청)를 내면 주방(AI 모델)이 요리(응답)를 내보냅니다. 웹의 채팅 화면 대신 내 코드가 직접 주문하므로, 엑셀을 읽은 결과를 바로 넘기고 결과를 바로 파일로 저장할 수 있습니다.

  • API 키: 내 계정으로 호출하는 사용자 증명이자 청구서 주소입니다. 비밀번호처럼 다루세요. 코드 파일, 메신저, 깃허브에 올리면 안 되고, 환경변수(ANTHROPIC_API_KEY)에 넣어 코드가 읽게 합니다. 유출되면 즉시 키를 폐기하고 새로 발급합니다.
  • 요금: 보낸 글과 받은 글의 토큰 수만큼 부과됩니다. 연습 때는 몇 건으로 작게 시작하세요.
  • 대화 기억이 없습니다: 매 호출은 독립적이어서 필요한 맥락(규칙, 데이터)을 매번 함께 보내야 합니다.
import anthropic
client = anthropic.Anthropic()     # 환경변수의 키를 자동으로 읽음

res = client.messages.create(
    model="claude-sonnet-5-5",      # 사용할 모델
    max_tokens=800,                 # 답변 길이 상한
    messages=[{"role": "user", "content": "...프롬프트..."}],
)
print(res.content[0].text)          # 답변 글

프롬프트 구조

프롬프트는 AI에게 주는 업무 지시서입니다. 신입 직원에게 일을 맡길 때처럼, 모호하게 "요약해 줘"라고 하기보다 아래 다섯 가지를 갖추면 결과가 안정됩니다.

  1. 역할: "너는 정산 점검 보조원이다"
  2. 맥락·데이터: 판단 근거가 되는 자료를 직접 붙여 준다 (모델이 지어내지 않게)
  3. 규칙: "주어진 데이터만 근거로 삼고, 없는 사실을 쓰지 마라"
  4. 출력 형식: "제목 1줄, 목록, 요청 사항 1~2줄 / 300자 안팎"
  5. 예시: 원하는 결과를 한두 개 보여 준다 (가장 강력한 방법)

나쁜 예: 이 지출 내역 정리해서 메일 써줘

좋은 예: 너는 정산 점검 보조원이다. 아래 JSON은 확인이 필요한 지출 목록이다. 담당자에게 보낼 메일 초안을 제목 1줄, 건별 목록, 요청 1~2줄로 써라. 목록에 없는 내용은 쓰지 마라.

구조화된 출력: JSON

코드가 AI의 답을 이어서 처리하려면 글이 아니라 정해진 형식으로 받아야 합니다. 가장 흔한 형식이 JSON입니다. 딕셔너리와 리스트를 글로 쓴 것이라고 생각하세요.

import json
items = json.loads(res.content[0].text)   # 글 → 파이썬 리스트/딕셔너리

AI의 답이 항상 올바른 JSON이라는 보장은 없으므로 두 가지를 반드시 합니다. 첫째, try/except로 파싱 실패를 잡아 한 번 더 시도하거나 사람에게 알립니다. 둘째, 값이 허용 범위인지 검사합니다(예: 문제 유형이 한도초과|증빙누락|증빙부적합 중 하나인지). 코드로 검증해야 하는 이유는 AI가 "그럴듯하지만 틀린" 값을 낼 수 있기 때문입니다.

한계와 안전한 사용

  • 환각: 판단 근거 데이터를 프롬프트에 직접 넣고, "모르면 모른다고 써라"를 지시하고, 숫자는 AI가 새로 쓰게 하지 말고 코드가 계산한 값을 그대로 쓰게 합니다.
  • 사람의 최종 검토: 메일 발송, 정산 판정처럼 결과가 상대에게 영향을 주는 단계는 초안까지만 자동화하고 사람이 읽고 보냅니다.
  • 프롬프트 인젝션: 엑셀 설명 칸에 "앞의 지시를 무시하고 …" 같은 문장이 들어 있을 수 있습니다. 외부에서 온 데이터는 "지시가 아니라 자료"라고 프롬프트에 명시하고, AI의 출력을 그대로 실행하거나 발송하지 않습니다.
  • 정보 보안: API로 보낸 내용은 외부 서비스로 전달됩니다. 개인정보(주민번호, 계좌, 연락처 등)와 기관 내부 자료는 보내기 전에 소속 기관의 정보보안 지침을 확인하고, 꼭 필요한 열만 골라 보내며, 가능하면 마스킹하세요.
  • 비용과 한도: 건수가 많으면 호출 횟수와 토큰이 곧 비용입니다. 규칙으로 걸러낸 의심 건만 AI에 보내면 비용도 줄고 정확도도 올라갑니다.

전체 흐름 한눈에

엑셀 읽기(pandas) → 규칙 점검(코드가 확정) → 의심 건만 AI에 전달 → 분류·요약문 생성(AI) → 파일 저장 → 사람이 검토 후 발송. 4주 동안 배운 모든 개념이 이 한 줄에 들어 있습니다.

복습 질문

1. 계산과 규칙 판정은 코드와 AI 중 누가 맡아야 하나요?

코드입니다. 코드는 같은 입력에 항상 같은 결과를 내지만, AI는 계산을 보장하지 않습니다. AI는 분류, 요약, 문장 작성을 맡습니다.

2. API 키는 어떻게 관리해야 하나요?

코드 파일에 직접 쓰지 않고 환경변수로 등록합니다. 메신저나 깃허브에 올리면 안 되고, 유출되면 즉시 폐기하고 새로 발급합니다.

3. AI에게 JSON으로 답을 받을 때 반드시 해야 할 두 가지는 무엇인가요?

파싱 실패를 잡아 재시도하거나 사람에게 알리는 것, 그리고 값이 허용된 범위 안에 있는지 코드로 검증하는 것입니다.

4. 점검에서 걸린 의심 건만 AI에 보내는 이유는 무엇인가요?

비용이 줄고, 정확도가 오르고, 외부로 나가는 정보도 최소화되기 때문입니다.

"""4주차: 점검 결과를 Claude API로 요약해 담당자용 메일 초안을 만든다.

준비
  1) pip install anthropic pandas openpyxl
  2) API 키를 환경변수로 등록 (코드에 직접 쓰지 마세요)
       Mac/Linux: export ANTHROPIC_API_KEY="발급받은 키"
       Windows:   setx ANTHROPIC_API_KEY "발급받은 키"
  3) week3/week3_rules_check.py 를 먼저 실행해 week3_issues.xlsx 를 만들어 두기

실행: python week4/week4_ai_summary.py

주의: 이 연습은 가상 데이터용입니다. 실제 업무 자료를 외부 API로 보내기 전에는
소속 기관의 정보보안 지침을 확인하고, 개인정보·계좌 등은 빼고 보내세요.
"""
import json
from pathlib import Path
import anthropic
import pandas as pd

BASE = Path(__file__).resolve().parent.parent
MODEL = "claude-sonnet-5-5"
client = anthropic.Anthropic()  # ANTHROPIC_API_KEY 환경변수를 자동으로 읽는다

issues = pd.read_excel(BASE / "week3_issues.xlsx")
rows = issues[["지출일", "사업명", "항목", "금액", "설명", "한도초과", "증빙누락", "증빙부적합"]]
data = rows.to_json(orient="records", force_ascii=False)

# 1) 구조화된 출력: 항목별로 위반 유형을 JSON으로 분류하게 한다.
classify_prompt = f"""너는 정산 점검 보조원이다. 아래 JSON은 규칙 점검에서 걸린 지출 목록이다.
각 건마다 아래 형식의 JSON 배열만 출력하라. 설명 문장은 쓰지 마라.
[{{"설명": "...", "문제": "한도초과|증빙누락|증빙부적합", "조치": "담당자가 할 일 한 문장"}}]
없는 사실을 지어내지 말고, 주어진 데이터만 근거로 삼아라.

{data}"""
res = client.messages.create(model=MODEL, max_tokens=1500, messages=[{"role": "user", "content": classify_prompt}])
text = res.content[0].text.strip().removeprefix("```json").removesuffix("```").strip()
items = json.loads(text)  # 형식이 틀리면 여기서 에러 -> 프롬프트를 고쳐서 다시 시도

# 2) 요약 메일 초안
mail_prompt = f"""아래 점검 결과로 사업 담당자에게 보낼 메일 초안을 써라.

- 어조: 정중하고 간결하게, 300자 안팎
- 금액은 천 단위 쉼표를 쓰고, 목록에 없는 내용은 쓰지 마라.

{json.dumps(items, ensure_ascii=False)}"""
res = client.messages.create(model=MODEL, max_tokens=800, messages=[{"role": "user", "content": mail_prompt}])
draft = res.content[0].text

out = BASE / "week4_mail_draft.txt"
out.write_text(draft, encoding="utf-8")
print(draft)
print(f"\n저장: {out}  (발송 전에 반드시 사람이 검토하세요)")

머신러닝·딥러닝 한 장 정리

직접 모델을 만들 일은 드물지만, 개념을 알면 외부 업체나 개발자와 자동화를 논의할 때 "이건 규칙으로 되는 일인가, AI가 필요한 일인가"를 스스로 가릴 수 있습니다.

포함 관계

AI ⊃ 머신러닝 ⊃ 딥러닝 순서로 범위가 좁아집니다. 4주차에서 쓴 LLM(Claude 같은 모델)은 딥러닝으로 만든 모델의 한 종류입니다.

기존 프로그래밍 vs 머신러닝

  • 기존 프로그래밍: 사람이 규칙을 쓰고, 컴퓨터가 규칙대로 결과를 낸다. (3주차의 한도·증빙 규칙 검사)
  • 머신러닝: 사람이 데이터와 정답을 주면, 컴퓨터가 규칙을 스스로 찾아낸다. 규칙을 글로 쓰기 어려운 일(사진 속 물체 알아보기, 스팸 메일 거르기)에 알맞습니다.

학습 방식 세 가지

종류 정답 여부 예시
지도학습 정답이 붙은 데이터로 학습 지출 설명을 보고 항목 분류, 다음 달 집행액 예측
비지도학습 정답 없이 비슷한 것끼리 묶기 비슷한 성격의 사업끼리 그룹화
강화학습 시도와 보상으로 학습 게임·로봇 제어

지도학습은 맞히는 대상에 따라 분류(종류 맞히기: 증빙 적합/부적합)와 회귀(숫자 맞히기: 집행액 예측)로 나뉩니다.

학습 과정과 과적합

  1. 데이터 준비: 입력과 정답이 짝을 이룬 예시를 모은다
  2. 학습: 모델이 오차를 줄이는 방향으로 스스로 조정한다
  3. 평가: 학습에 쓰지 않은 새 데이터로 시험한다
  4. 사용: 실제 업무 데이터에 적용하고 계속 점검한다

과적합(overfitting) 은 연습문제 답만 외워서 실전 시험은 못 보는 상태입니다. 학습 데이터에서는 거의 완벽한데 새 데이터에서는 틀립니다. 그래서 데이터를 학습용과 평가용으로 나눠 놓고 평가용으로만 성적을 확인합니다.

딥러닝

사람 뇌의 신경망을 흉내 낸 층이 아주 많은 모델로 학습하는 방식입니다. 이미지·음성·언어처럼 규칙을 사람이 만들기 어려운 데이터에 강하지만, 대량의 데이터와 연산 자원이 필요합니다. 엑셀 같은 표 형태 데이터는 전통적인 머신러닝이나 규칙만으로 충분한 경우가 많습니다.

업무에서는 무엇을 쓸까

  1. 규칙으로 쓸 수 있으면 규칙(코드) 이 가장 정확하고 설명하기 쉽습니다. (3주차)
  2. 글을 분류·요약·작성하는 일은 LLM API로 해결합니다. 모델을 직접 만들 필요가 없습니다. (4주차)
  3. 직접 모델을 학습하는 일은 정답이 붙은 데이터가 충분히 쌓였고 위 두 방법으로 풀리지 않을 때 검토합니다.
